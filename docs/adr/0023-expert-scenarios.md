# ADR 0023：专家常用场景与内置专家场景覆盖

- 状态：接受（2026-09-26）。产品侧设计见产品仓库 ADR 0027 与 `docs/specs/2026-09-26-scenario-home-b-to-a.md`。
- 在 [ADR 0022](0022-expert-distribution.md) 的专家分发之上增加两件事：云端专家可以带“常用场景”，官网可以替换随产品发布的
  内置专家的常用场景。契约版本仍为 1，协议包升级到 0.1.1。

## 背景

常用场景是一位专家的“带标题的提问模板”。使用者在工作助手的新对话首页或专家卡片上点一下场景，提问模板被填进输入框，
改完 `【】` 里的内容再发送——只填入，从不自动发送。场景属于专家（不建独立的场景库）。运营希望在官网直接维护云端专家的场景，
并能在不发版的情况下调整随安装包发布的五位内置专家的场景。

## 决策

**场景结构与规则来自契约包。** `@dsh-ops/expert-distribution-contract/scenarios`（不依赖 zod，官网后台页面直接打包）定义
`{ id, title, summary?, prompt, modeId?, icon? }` 与上限：每位专家最多 8 个；名称 ≤16 字、简介 ≤40 字、提问模板 ≤300 字（按字符计）；
模板最多 3 处 `【】`；名称与简介不能换行；ID 为小写短横线格式且唯一，名称唯一；模板里不能出现疑似密钥或令牌；`modeId` 只能是
`ppt`、`design`、`skill-studio`（缺省为日常办公）；`icon` 只能是契约 `SCENARIO_ICONS` 的 16 个名称之一（缺省时按工作模式、再按专家图标自动配图，见 `scenarioIconFor`），图形统一取自 `SCENARIO_ICON_SHAPES`。写入一律严格（`scenarioIssues` / `ScenariosSchema`），读取一律宽松
（`normalizeScenarios` 丢弃坏条目，不丢专家）。旧的 `starterPrompts` 保持原样，不转换为场景。

**云端专家的场景跟随专家版本。** 草稿、记录与发布快照中的 `scenarios` 为可选字段：空列表存为“没有这个键”，因此没有场景的专家
摘要不变（不会被标为“有未发布修改”），场景出现之前写入的快照照常解析。保存草稿即按严格规则校验（`INVALID_EXPERT`，逐条注明
“常用场景第 N 个”），发布前再核一次（`EXPERT_NOT_PUBLISHABLE`）。导入专家包时映射 `expert.json` 的 `scenarios`，重新导入的预览
按场景 ID 列出新增、修改、移除与顺序变化。专家包格式是严格的：带未知字段（例如 `automationTemplateId`）的场景整包拒绝，而不是悄悄丢弃。
工作助手导出带场景的专家时把场景名称写进 `starterPrompts`（给不读场景的一方看）；官网导入时不保存这份派生的名称——更新已有专家时保留它原有的
Prompt 建议，新建则为空——否则删光场景后，过期的场景名称会作为后台无法编辑的旧版 Prompt 建议继续下发。有场景时目录总会重新派生这些名称。

**新字段只下发给会读的客户端。** 在场景出现之前构建的工作助手会拒绝目录中的未知字段，因此公开目录只有在请求头
`X-Ops-Expert-Features: scenarios` 出现时才返回 `experts[].scenarios` 与信封上的 `builtinScenarios`。无论是否带这个请求头，
有场景的专家其 `starterPrompts` 都改为场景名称（旧客户端据此显示 Prompt 建议，两边一致）。ETag 同时按工号与所请求的特性计算，
响应带 `Vary: X-Ops-Employee-Id, X-Ops-Expert-Features`；不带特性的请求沿用原来的 ETag 计算方式，旧客户端不因升级失去 304。

**内置专家场景按专家整体替换。** 官网只认识 `BUILTIN_EXPERTS` 列出的五位内置专家的 ID 与名称，看不到安装包里的原始场景。
一条已发布的覆盖就是这位专家的完整场景列表（替换，不合并；发布空列表即隐藏随产品发布的场景）；没有覆盖就是随产品发布的内容。
覆盖对所有人生效（包括未识别工号的使用者），不按可见范围筛选。存储为 `<contentDirectory>/experts/builtin-scenarios.json`
（schemaVersion 1，revision 为内容摘要），每位专家一份草稿与可选的已发布版本 `{ version, publishedAt, scenarios }`；与专家目录共用
`.experts-lock`、同目录临时文件加改名，每次覆盖前把旧文件备份到 `.trash/`，写接口携带 revision，不一致返回 409。
“恢复为随产品发布”删除这位专家的覆盖与草稿。公开目录的 `builtinScenarios` 只列出已发布的覆盖，按内置专家顺序排列；没有覆盖时不带这个键。
这个文件损坏只影响读取场景的客户端（503），旧客户端的目录不受影响。

**管理接口用独立前缀。** `/api/admin/expert-builtin-scenarios`（`GET` 列表；`PUT /:expertId` 保存草稿 `{revision, scenarios}`；
`POST /:expertId/publish`；`DELETE /:expertId` 恢复为随产品发布）。放在 `/api/admin/experts/` 下会被专家 ID 路由吞掉。
未知 ID 返回 404 `BUILTIN_EXPERT_NOT_FOUND`，场景不合规返回 400 `INVALID_SCENARIOS`。鉴权、同源与 CSRF 与其他后台接口相同。

**后台沿用现有组件。** 共享的 `ScenarioListEditor.vue` 逐行编辑（添加、编辑、上移、下移、删除；名称与简介带字数、模板提示 `【】`
用法、工作模式用单选组；图标是一组方形单选按钮：第一个“自动”预览产品会自动配的图形，其余 16 个用契约的中文名做无障碍名称，方向键在组内移动并选中、Home/End 跳到首尾，整组只占一个 Tab 位；行首显示产品同款图标、工作模式显示为小标签），行内表单而非嵌套弹窗，Escape 只关闭行内表单，回车保存这一行（不提交外层表单），删除用应用内确认框，按契约规则
就地校验（包括改名与其他任一行重名）。云端专家表单用它替换原来的“Prompt 建议”文本框（`starterPrompts` 保留原值、不再编辑）；打开着的场景行
算作未保存的修改，保存草稿、发布、上传或移除技能前须先保存或取消，保存分发设置与下架不会关掉它。“专家分发”增加第三个页签“内置专家场景”，
左侧列出五位内置专家与状态（随产品发布 / 已覆盖 · 发布于… / 有未发布修改），右侧保存草稿、发布（确认“发布后，所有同事下次同步时生效”；
没有可发布的改动时不可用）与恢复为随产品发布（确认；只在已发布覆盖或已保存草稿时出现）。

**升级顺序：官网先行。** 目录方向（官网 → 工作助手）可以任意顺序升级：旧客户端不带特性请求头，收不到新字段。导入方向（工作助手导出 → 官网）
不行：契约 0.1.0 的专家包格式是严格的，旧官网会以 `INVALID_EXPERT_PACKAGE`（未知字段 `scenarios`）拒绝带常用场景的专家包。因此官网
（契约 0.1.1）必须先于会导出常用场景的新版工作助手部署；没有场景的专家包不带这个字段，新旧官网都能导入。

## 结果

运营可以不发版地维护云端专家与内置专家的常用场景；新旧工作助手都能读同一个目录。

代价：官网多一个覆盖文件与一组后台接口；内置专家的原始场景只在产品仓库，后台无法展示“随产品发布”的具体内容（当前产品不随包提供场景）。
未来的 `needs`、`deprecated` 等字段需要按“先契约、再官网、后客户端”的顺序以新特性名追加。
